> 文档状态：评审稿<br>
> 版本：V0.9<br>
> 日期：2026-08-25<br>

## 1. 架构目标

架构需要在当前开发资源和生产约束下，实现“持续取数—确定性分析—AI 建议—JIRA 跟进—效果验证”的可靠闭环，并为未来替换数据中台接口、LDAP 和内部大模型网关保留稳定边界。

核心目标：

- **可解释**：异常结论、建议和动作均能追溯至原始快照、规则和知识版本。
- **可重复**：确定性分析不依赖大模型随机输出。
- **可恢复**：定时任务失败可重试，外部写操作幂等，服务重启不丢治理状态。
- **权限隔离**：用户只能查询和操作其授权系统。
- **渐进演进**：第一阶段使用模块化单体和现有 MySQL 5.7/Redis，避免过早引入重型基础设施。
- **拟人化但不失控**：用户面对一个 Capacity Agent，后台持续产生可见工作事件；生产变更始终由人审批和执行。

## 2. 架构原则与关键决策

### 2.1 用户单 Agent，内部能力模块化

产品层只呈现一个 Capacity Agent，避免用户在“数据 Agent、建议 Agent、任务 Agent”之间切换。内部将职责拆成采集、分析、知识检索、建议、治理编排、JIRA、验证和对话等模块，通过明确的数据对象串联。

第一阶段不拆微服务：团队规模、部署环境和当前吞吐尚不足以抵消分布式事务、链路追踪和运维成本。模块边界保持清晰，未来可按采集、AI 或任务吞吐独立拆分。

### 2.2 MySQL 是事实源，Redis 是运行时设施

- MySQL 5.7 保存资源、证据、发现、建议、治理事项、JIRA 映射、知识、记忆和审计。
- Redis 用作 Celery Broker、短期结果、分布式互斥、SSE 事件扇出和短缓存。
- Redis 数据丢失后，任务状态和治理闭环可由 MySQL 重建。
- 第一阶段不将向量库作为必需依赖；知识检索使用 MySQL FULLTEXT ngram + Python 侧轻量向量/重排。后续可增加 Qdrant 作为可重建索引，不改变 MySQL 的事实源地位。

### 2.3 规则定结论，模型做综合

- 数据质量、特征、最终状态、严重度、置信度和自动建单门槛由确定性代码和版本化规则计算。
- 大模型输入是经过权限过滤和证据装配的结构化上下文。
- 大模型输出必须通过 JSON Schema 校验，并验证所有证据引用真实存在且属于同一分析范围。
- 模型不可直接调用生产变更工具，也不可自行提升自动化权限。

### 2.4 事件驱动体验，持久化工作流

Agent 的“正在工作”不是前端动画，而是后端任务执行产生的 `agent_event`。前端通过 SSE 订阅授权系统的工作事件。任务状态、重试和下一次执行时间持久化到 MySQL；Celery/Redis 只负责调度和执行。

## 4. 模块职责

| 模块 | 主要职责 | 不负责 |
|---|---|---|
| API/BFF | REST/SSE、输入校验、响应聚合、错误映射 | 直接执行长任务 |
| IAM | 模拟登录、用户系统授权、服务端数据范围 | 第一阶段 LDAP 协议实现 |
| Resource Catalog | 系统、组件类型、逻辑资源、实例、链路、集群和身份匹配 | 性能异常判定 |
| Collector | 调用四接口、重试、快照、schema 校验和标准化 | AI 建议 |
| Evidence | 证据项、派生特征、引用关系和只读证据视图 | 修改原始快照 |
| Analysis | 数据质量门禁、动态基线、趋势、预测、规则、归并和置信度 | 自由文本生成 |
| Knowledge | 文档版本、审核发布、切分、检索和引用 | 当前性能事实存储 |
| Memory | 历史案例、偏好、反馈和有效期 | 作为异常判定的最高优先依据 |
| Recommendation | 组装上下文、调用模型、结构校验、引用校验和建议发布 | 直接创建生产变更 |
| Governance | 治理事项状态机、自动化门槛、观察策略和验证 | 替代 JIRA 执行工作流 |
| Jira Adapter | JIRA API v2、字段映射、幂等建单、webhook 和对账 | 硬编码企业字段 ID |
| Agent Orchestrator | 计划任务、能力调用、工作事件、主动消息和会话上下文 | 把业务状态仅放在内存中 |
| Audit | 外部操作、权限、规则、知识、检索和模型调用审计 | 业务查询模型 |

## 7. 采集与标准化设计

### 7.1 适配器协议

每个外部数据源实现统一接口：

```python
class SourceAdapter(Protocol):
    source_type: SourceType

    async def fetch(self, request: SourceRequest) -> RawSourceResponse: ...
    def validate(self, response: RawSourceResponse) -> ValidationResult: ...
    def normalize(self, response: RawSourceResponse) -> NormalizedBatch: ...
```

第一阶段实现：

- `MockDailySummaryAdapter`
- `MockMetricHistoryAdapter`
- `MockServerHardwareAdapter`
- `MockSystemProfileAdapter`

真实接口接入时只替换 Adapter 和配置，不修改分析模块。

### 7.2 快照与幂等

- 一次 `collection_run` 代表某系统、某业务日期的一轮采集。
- 每个数据源响应生成本轮独立的 `source_snapshot`，以 `collection_run_id + source_type + request_key` 保证单轮幂等，并用 `payload_hash` 识别跨轮重复内容。
- 原始 payload 以 JSON 保存；非标准文本先包装为 `{rawText: ...}`。
- 标准化数据携带 `snapshot_id`，任何派生数据都可回到原始响应。
- 重跑同一业务日期默认创建新 run；相同 payload 仍保存本轮快照记录并标识内容重复，分析结果记录新的 run 版本。

### 7.3 资源身份解析

`ResourceIdentityResolver` 根据统一资源 ID、SN、hostname、IP 和组合键产生：

```json
{
  "instanceId": 123,
  "matchMethod": "HOSTNAME_EXACT",
  "confidence": 0.95,
  "conflicts": []
}
```

有冲突或非唯一匹配时不写入错误归属，而是生成数据质量发现。画像中的拓扑归属按快照版本保存，不能用最新画像改写历史分析。

## 8. 分析流水线

```text
Normalized Metrics
  → Quality Gate
  → Feature Builder
  → Rule Evaluator
  → Architecture Context Evaluator
  → Finding Grouper
  → Action Policy
```

### 8.1 Quality Gate

检查时间序列长度、时间与数值一一对应、`min <= avg <= max`、数值范围、身份关联、画像新鲜度和指标完整度。错误分为：

- `BLOCKING`：阻止自动判定/建单；
- `DEGRADED`：允许保守分析，但降低可用证据权重；
- `INFO`：仅记录。

### 8.2 Feature Builder

输出版本化结构：

- 当前窗口：avg/max/min；
- 持续性：近 N 日越界次数、连续次数；
- 动态基线：median、MAD、deviation score；
- 趋势：slope、R²、threshold ETA；
- 集群：min/max/range/CV、异常节点占比；
- 治理前后：baseline window、observation window、improvement rate。

特征必须保存计算版本和参数，不能只保存最终文案。

### 8.3 Rule Evaluator

规则由 `scope + condition + effect + version` 组成。第一阶段规则条件采用受控 JSON DSL，不执行用户输入的 Python/SQL。例如：

```json
{
  "all": [
    {"field": "metric", "op": "eq", "value": "DISK"},
    {"field": "current.max", "op": "gte", "value": 90},
    {"field": "resource_match_confidence", "op": "gte", "value": 0.8}
  ]
}
```

规则效果只能来自白名单：设置候选状态、严重度、证据标签、豁免或要求人工复核。冲突时按范围优先级、显式优先级和版本生效时间裁决，并保存所有命中记录。

### 8.4 Finding Grouper

归并器根据发现指纹和拓扑，将同一根因的多个实例信号归并为系统/逻辑资源级发现。归并不会删除实例级证据；父发现通过关联表引用全部证据。

## 9. 知识、记忆与检索

### 9.1 数据职责分离

| 数据层 | 回答的问题 | 可靠性要求 |
|---|---|---|
| 当前证据 | “现在发生了什么？” | 原始快照不可变，可复算 |
| 治理知识 | “制度和手册要求怎么做？” | 版本化、审核、发布、有效期 |
| 已验证案例 | “类似问题以前怎么处理、效果如何？” | 必须有关联发现、治理和验证结果 |
| Agent 记忆 | “这个用户/系统有哪些稳定偏好和上下文？” | 来源、置信度、有效期、可反馈 |
| 模型通用知识 | “如何组织解释和补充一般性建议？” | 最低优先级，必须显式标注 |

检索优先级固定为：`当前证据 > 已发布治理知识 > 已验证案例 > 有效记忆 > 模型通用知识`。

### 9.2 知识处理

```text
文档导入 → 版本生成 → 元数据校验 → 标题感知切分
→ FULLTEXT/轻量向量索引 → 人工审核 → 发布 → 检索引用
```

- 原文和版本元数据存 MySQL。
- Chunk 保留标题路径、段落序号、来源位置和适用范围。
- 中文关键词检索使用 MySQL 5.7 ngram FULLTEXT；第一阶段可在 Python 侧对候选集进行向量重排。
- 如果后续引入 Qdrant，仅同步 `PUBLISHED` chunk，索引可由 MySQL 重建。

### 9.3 记忆分层

- L0 工作轨迹：原始对话和 Agent 事件；
- L1 事实记忆：系统别名、负责人偏好、已确认约束；
- L2 案例记忆：发现—建议—JIRA—验证闭环摘要；
- L3 稳定模式：多次验证有效的处置模式，仍不能绕过知识发布和规则审批。

记忆写入异步执行。模型提炼内容先带 `UNVERIFIED`，只有人工确认或治理验证支持后才可提升可信等级。

### 9.4 检索审计

每次 AI 调用保存 query、权限范围、过滤条件、候选条目、排序分数、最终选中条目和未命中原因。这样可以解释“模型为什么引用了这条制度”。

## 10. Agent 编排与任务设计

### 10.1 任务类型

| 任务 | 触发 | 幂等键示例 |
|---|---|---|
| 每日系统采集 | Beat/人工重跑 | `collect:{system}:{date}:{source}` |
| 系统分析 | 采集完成 | `analyse:{collection_run}` |
| 建议生成 | 新发现/证据更新 | `recommend:{finding}:{evidence_version}` |
| JIRA 建单 | 行动策略 | `jira-create:{governance_case}` |
| JIRA 对账 | 每 10 分钟 | `jira-sync:{tenant}:{window}` |
| 观察采样 | 每日 | `verify-sample:{case}:{date}` |
| 最终验证 | 观察期到期 | `verify-final:{case}:{policy_version}` |
| 记忆提炼 | 会话/治理完成 | `memory-distill:{source_type}:{source_id}` |

### 10.2 MySQL 5.7 任务租约

MySQL 5.7 不支持 `SKIP LOCKED`。第一阶段由 Celery 分发，MySQL 持久化 `workflow_job`，领取任务时使用带版本号的条件更新：

```sql
UPDATE workflow_job
SET status='RUNNING', lock_token=?, locked_until=?, version=version+1
WHERE id=? AND version=?
  AND status IN ('PENDING','RETRYING')
  AND (locked_until IS NULL OR locked_until < NOW(3));
```

只有受影响行数为 1 才获得租约。Worker 崩溃后由 `locked_until` 超时恢复。所有外部写操作另有业务幂等键，不能只依赖任务不重复执行。

### 10.3 工作事件与主动消息

任务每个用户可理解阶段写入 `agent_event`，事件类型包括：

- `PLAN_CREATED`
- `DATA_FETCH_STARTED/COMPLETED/FAILED`
- `ANALYSIS_STARTED/COMPLETED`
- `FINDING_CREATED/UPDATED`
- `RECOMMENDATION_READY`
- `JIRA_CREATED/SYNCED/OVERDUE`
- `OBSERVATION_STARTED/PROGRESS`
- `VERIFICATION_SUCCEEDED/FAILED`

SSE 只负责实时推送；事件先写 MySQL，再通过 outbox 发布到 Redis，保证页面刷新后仍能恢复完整工作记录。

## 11. JIRA 集成架构

### 11.1 适配器边界

```python
class JiraGateway(Protocol):
    async def create_issue(self, command: CreateIssueCommand) -> JiraIssueRef: ...
    async def add_comment(self, issue_key: str, body: str) -> None: ...
    async def transition(self, issue_key: str, transition: str) -> None: ...
    async def get_issue(self, issue_key: str) -> JiraIssueSnapshot: ...
```

提供 `MockJiraGateway` 和 `JiraServerV2Gateway`。业务模块只使用内部 Command/DTO，不依赖 JIRA 原始 JSON。

### 11.2 一致性策略

```text
本地事务：治理事项 + JIRA 创建请求 + outbox
→ 异步调用 JIRA
→ 成功：保存 issueKey/issueId/状态快照
→ 超时：按 idempotency_key 进入 UNKNOWN，先核对再重试
→ 失败：指数退避；超过阈值进入人工处理
```

JIRA webhook 入口验证来源并快速落库，异步处理；定时对账作为最终一致性保障。Webhook 和轮询都以 `jira_issue_id + updated` 去重。

| POST | `/knowledge/versions/{id}/submit` | 提交审核 |
| POST | `/knowledge/versions/{id}/publish` | Admin 发布 |
| GET/PUT | `/admin/rules` | 规则查询与版本化修改 |
| GET/PUT | `/admin/jira-mappings` | JIRA 字段与状态映射 |
| GET/PUT | `/admin/verification-policies` | 观察和验证策略 |

## 13. 大模型网关设计

统一 `LlmGateway` 使用 OpenAI 兼容协议，环境差异仅通过配置：

| 配置 | 开发 | 生产 |
|---|---|---|
| `base_url` | DeepSeek 公网 API | 公司内部网关 |
| `api_key` | 开发密钥 | 内部凭据 |
| `model` | 配置化 | 配置化 |
| 网络 | 公网 | 内网 |

请求设置超时、重试、最大 token 和温度；建议生成使用低温度和 JSON Schema。保存模型名、网关类型、提示模板版本、输入摘要 hash、token 使用量、耗时和结果状态，不保存密钥。

模型不可见全库，只接收经过权限与范围裁剪的 `AnalysisContext`。对接口文本、JIRA 描述和知识内容做数据边界标记，忽略其中试图修改系统指令或工具权限的内容。

## 14. 部署架构

### 14.1 开发测试部署

采用开发服务器 1，复用现有 MySQL 5.7、Redis 7.x 和 Nginx；本项目自身不使用 Docker：

```text
/opt/capacity-agent/
├── releases/<version>/
│   ├── backend/
│   └── frontend-dist/
├── current -> releases/<version>
├── shared/.env
└── logs/
```

systemd 单元：

- `capacity-agent-api.service`：FastAPI/Uvicorn，监听 `127.0.0.1:8500`；
- `capacity-agent-worker.service`：Celery Worker，第一阶段并发 1；
- `capacity-agent-beat.service`：Celery Beat，仅运行一个实例。

Nginx：

- `/capacity-agent/` 提供前端静态资源；
- `/capacity-agent-api/` 反向代理 API；
- SSE 路径设置 `proxy_buffering off`。

开发服务器 2 继续承载现有静态演示，不作为正式后端节点。正式部署前仍需再次检查目标服务器状态，并在用户确认后进行数据库、Nginx 和 systemd 写操作。

### 14.2 容量边界

当前开发服务器资源适合单 API Worker、单 Celery Worker 和单 Beat 的演示/开发负载。不在同机部署 Qdrant、Temporal、本地 BGE 或本地大模型。若系统数、实例数或对话并发增长，优先拆出 Worker 并增加外部基础设施，而不是在单机无界提高并发。

## 15. 可观测与运行保障

### 15.1 指标

- 四接口调用成功率、延迟、数据新鲜度和 schema 失败数；
- 巡检耗时、任务积压、重试、死信和租约超时数；
- 规则命中、发现数量、归并率、人工确认准确率；
- 模型延迟、失败率、结构校验失败率和证据引用失败率；
- JIRA 建单成功率、去重率、同步延迟和未知状态数；
- 观察中事项、验证成功率、验证失败和重复异常率；
- SSE 在线数、重连数和事件延迟。

### 15.2 日志与追踪

日志使用结构化 JSON，关联键包括 `request_id`、`job_id`、`inspection_run_id`、`finding_id`、`governance_case_id` 和 `jira_issue_key`。不得记录密码、Token、完整模型密钥或未经脱敏的敏感 payload。

### 15.3 失败降级

| 故障 | 降级行为 |
|---|---|
| 单一数据源不可用 | 保存失败快照并重试；使用旧数据时明确标注，不自动建新 JIRA |
| 系统画像不可用/过期 | 允许展示原始指标；低利用和角色相关判断进入 NEEDS_REVIEW |
| 大模型不可用 | 规则结论和证据仍可发布；建议状态为待生成，不阻塞高风险告警/建单模板 |
| JIRA 不可用 | 治理事项保持待建单并重试；不伪造 issue key |
| Redis 不可用 | API 可只读查询 MySQL；后台任务暂停，恢复后从 workflow_job/outbox 续跑 |
| SSE 断开 | 前端轮询简报并在重连后按 event_id 补拉 |

1. **MVP**：Mock 四接口、模拟登录、规则分析、DeepSeek、Mock JIRA、核心页面。
