# Capacity Agent 性能容量治理平台核心数据模型

> 文档状态：评审稿<br>
> 版本：V0.9<br>
> 日期：2026-08-25<br>
> 数据库基线：MySQL 5.7，字符集 `utf8mb4`，时区统一存 UTC

## 1. 建模目标

核心数据模型必须支持：

1. 系统、组件类型、逻辑资源、服务器实例和多管理员授权；
2. 四接口原始快照、标准化指标和系统画像历史版本；
3. 可复算的特征、规则命中、分析发现和证据引用；
4. 治理建议、JIRA、观察和效果验证的完整状态机；
5. Agent 工作事件、对话、知识、记忆和审计；
6. MySQL 5.7 下可恢复、幂等的异步任务。

## 2. 设计约定

- 数据库内部主键使用 `BIGINT UNSIGNED AUTO_INCREMENT`，对外标识使用应用生成的 ULID `CHAR(26)`。
- 表名和字段名使用英文蛇形命名；状态值使用大写英文枚举字符串。
- 时间使用 `DATETIME(3)` 存 UTC；业务日期使用 `DATE`。
- 金额、百分比和指标值使用 `DECIMAL`，不使用浮点数保存判定依据。
- 原始接口响应、规则条件、特征和模型结构化输出使用 MySQL 5.7 原生 `JSON`。
- JSON 只承载来源结构或可变扩展；需要筛选、关联和约束的核心字段必须列化。
- MySQL 5.7 不可靠执行 `CHECK` 约束，枚举、范围和状态迁移由应用层校验并由测试覆盖。
- 事实记录不物理删除；配置类数据使用 `is_enabled` 或状态字段，历史使用版本表。
- 所有用户查询先计算授权 `system_id` 范围，再访问业务表。

## 3. 领域关系

```text
User ──< UserSystemRole >── System
System ──< ComponentType ──< LogicalResource ──< InstanceMembership >── Instance
System ──< ProfileSnapshot ──< Topology/Link/Cluster

InspectionRun ──< SourceSnapshot ──< DailyMetric / MetricSample
InspectionRun ──< AnalysisRun ──< Feature / RuleHit / Finding >── EvidenceItem
Finding ──< Recommendation ──< GovernanceCase ──1 JiraLink
GovernanceCase ──< VerificationRun ──< VerificationSample

KnowledgeDocument ──< KnowledgeVersion ──< KnowledgeChunk
Conversation ──< Message
AgentEvent、MemoryItem、WorkflowJob、OutboxEvent、AuditLog 横向关联上述对象
```

## 5. 状态机

### 5.1 分析发现

```text
OPEN → ACKNOWLEDGED → GOVERNING → RESOLVED → CLOSED
  ├──────────────────────────────→ SUPPRESSED
  └──────────────────────────────→ CLOSED
```

- `SUPPRESSED` 必须记录规则、有效期或人工理由。
- 治理事项验证通过后，关联发现转 `RESOLVED`；下一轮未复发且关闭条件满足后转 `CLOSED`。
- 同一指纹复发时可重新打开原发现或创建新 occurrence，策略由去重窗口决定。

### 5.2 治理事项

```text
PROPOSED
├─ 确认异常 ───────────────→ TICKET_PENDING
├─ 优化机会 → WAITING_CONFIRMATION → TICKET_PENDING
└─ 证据不足 ───────────────→ NEEDS_REVIEW

TICKET_PENDING → TICKET_OPEN → TICKET_IN_PROGRESS
→ OBSERVING → VERIFYING
              ├─ PASS → VERIFIED
              ├─ FAIL → VERIFICATION_FAILED → TICKET_IN_PROGRESS / NEEDS_REVIEW
              └─ INCONCLUSIVE → OBSERVING / NEEDS_REVIEW

非终态可在有理由时 → CANCELLED
```

状态迁移必须写 `governance_case_event`，不得只更新当前状态。

## 8. 关键数据不变量

以下不变量必须由服务层事务和测试保证：

1. 一个用户只能访问 `iam_user_system_role` 当前有效范围内的系统，Admin 除外。
2. `metric_daily_summary` 必须满足 `min_value <= avg_value <= max_value` 才能标为 `VALID`。
3. 每个 `evidence_item` 必须属于一个 `analysis_run` 和一个系统。
4. 发布的 `recommendation` 至少有一个有效证据引用，且所有引用系统范围一致。
5. 只有 `ANOMALY` 且满足门槛的发现可自动创建治理事项/JIRA；优化机会必须有确认事件。
6. 一个活动去重键最多对应一个活动发现和一个活动治理事项。
7. `jira_issue_link.issue_key` 不得在外部创建成功前伪造。
8. JIRA 完成只能把治理事项推进到 `OBSERVING`，不能直接推进到 `VERIFIED`。
9. `verification_run` 保存策略和条件快照；后续策略更新不能改变历史验证标准。
10. 只有 `PUBLISHED` 且在有效期内的知识版本能进入正式检索。
11. 记忆不能覆盖当前证据或已发布规则；过期/拒绝记忆不参与检索。
12. Agent 事件先持久化，再推送；SSE 丢失不影响业务状态。

## 9. 索引与数据量策略

### 9.1 高频查询索引

- 系统/日期：`metric_daily_summary(system_id, business_date, metric)`；
- 实例趋势：`metric_sample(instance_id, metric, sample_time)`；
- 未结发现：`analysis_finding(system_id, status, severity)`；
- 用户任务：`governance_case(assigned_user_id, status)`；
- Agent 增量事件：`agent_event(system_id, id)`；
- 待执行任务：`workflow_job(status, available_at, priority)`；
- 待发布事件：`outbox_event(status, available_at, id)`。

### 9.2 保留策略建议

| 数据 | 在线保留 | 归档策略 |
|---|---:|---|
| 原始接口快照 | 180 天 | 压缩归档；hash、元数据和引用长期保留 |
| 日汇总指标 | 至少 3 年 | 按年评估归档 |
| 细粒度历史样本 | 1 年或遵从数据源 | 可按日聚合后归档 |
| 发现、建议、治理、验证 | 长期 | 不物理删除 |
| Agent 事件 | 180 天在线 | 关键治理事件长期保留在 case event |
| 对话 | 按企业合规策略 | 删除前解除/匿名化记忆来源 |
| 审计 | 至少 1 年 | 按安全合规要求调整 |

MySQL 5.7 第一阶段不启用分区表，先用上述复合索引和批量归档。达到千万级时根据真实查询和写入量评估按时间分区或冷热库，避免预先复杂化。

## 10. 事务边界

| 操作 | 同一数据库事务内 |
|---|---|
| 完成采集 | 快照元数据、标准化数据、collection 状态、outbox |
| 发布发现 | finding、evidence links、rule hits、case（如适用）、agent event、outbox |
| 确认优化建议 | case 状态、确认人、case event、JIRA job、outbox |
| JIRA 回调 | jira snapshot、case 状态、case event、agent event、outbox |
| 验证完成 | verification result、case 状态、finding 状态、case event、memory job、outbox |
| 知识发布 | version 状态、current version、审核记录、reindex job、audit |

外部 JIRA 和大模型调用永远不放在数据库事务中；使用任务、幂等键和 outbox 保证最终一致。

## 11. 数据迁移与兼容

- 所有 schema 变更使用向前 migration，不手工修改生产表。
- 第一阶段真实工程建立后，migration 在空 MySQL 5.7 实例和含样例数据实例各验证一次。
- 新增字段优先可空或有安全默认值，数据回填与约束收紧分两次发布。
- 外部接口 schema 通过 `source_snapshot.schema_version` 和适配器版本隔离。
- 未来数据中台接入时保留现有标准化表，旧快照继续可追溯。
- LDAP 接入只改变 `iam_user.user_type/external_dn` 和登录适配器，不改变用户系统授权关系。

## 12. 模拟数据最小关联场景

正式工程的 seed 数据至少包含：

1. 3 个系统（A/B/C 重要性），4 个用户（两个系统管理员、一个跨系统 SRE、一个 Admin）。
2. 每个系统至少 2 个组件类型、2 个逻辑资源和 3 个服务器实例。
3. 四接口使用相同 hostname/SN/IP，可生成精确关联，也包含一条身份冲突和一条不支持硬件信息。
4. CPU、内存、磁盘各有昨日 avg/max/min 和 30 日历史；另构造一条磁盘历史缺失。
5. 覆盖 P1 磁盘增长、P2 集群倾斜、低利用优化、冷备预期偏离和数据质量待复核。
6. 一条异常自动建 Mock JIRA，一条优化建议等待确认，一条 JIRA 完成后验证失败。
7. 每个建议至少引用 2 条数据证据和 1 条已发布模拟管理办法；草稿知识不应被检索。

这组数据是后续前后端联调和需求 AC-01 至 AC-12 的共同验收基线。
