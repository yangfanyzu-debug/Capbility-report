# Capacity Agent 性能容量治理平台需求规格说明

> 文档状态：评审稿<br>
> 版本：V0.9<br>
> 日期：2026-08-25<br>
> 范围：第一阶段正式工程，不包含 Vue/FastAPI 工程创建和真实生产系统变更

## 1. 文档目的

本文定义 Capacity Agent 第一阶段的产品范围、角色权限、业务流程、四个输入接口、异常策略、治理闭环及验收标准。本文经确认后，作为 Vue 3 + FastAPI 工程设计、开发与测试的基线。

## 2. 背景与目标

现有接口能够提供昨日性能汇总、单实例历史趋势、服务器硬件信息和系统画像，但数据分散、基线状态缺少架构语义，异常发现与治理执行也未形成闭环。

平台目标是让 Capacity Agent 像一名持续值守的容量同事：每天自主取数和分析，主动呈现发现与依据，对确认异常创建并跟进 JIRA，在治理完成后按配置观察并验证效果，同时允许用户通过对话追问、纠正分析方向或发起专项分析。

第一阶段业务目标：

1. 将四个接口的数据标准化并建立可追溯证据。
2. 从系统、组件类型、逻辑资源和服务器实例四层展示性能容量结论。
3. 用确定性策略识别高使用率、低使用率、增长风险、负载倾斜和数据质量问题。
4. 由大模型基于数据证据、系统画像和已发布治理知识生成解释与建议。
5. 对确认异常由 Agent 主动创建 JIRA；对优化机会先由负责人确认。
6. 持续同步 JIRA 状态，在完成后进入观察周期并自动验证效果。
7. 通过聊天、工作事件和任务面板体现 Agent 的自主工作过程。

## 3. 范围

### 3.1 第一阶段包含

- 模拟登录及基于系统授权的数据隔离；
- 每日定时巡检和人工发起专项分析；
- 四个接口适配、原始快照留存、标准化和数据质量检查；
- CPU、内存、磁盘的平均值、峰值、最小值和历史趋势分析；
- 系统画像关联、组件/逻辑资源/实例归属和拓扑上下文；
- 规则判定、异常归并、证据链和 AI 治理建议；
- JIRA Server 8.13.4 的建单、状态同步、评论和完成后验证；
- 首页对话、今日巡检简报、正在跟进任务、系统下钻、证据页、治理任务页和知识管理页；
- 模拟数据、模拟 JIRA 和真实 JIRA 适配器的可切换设计；
- 性能容量管理办法等模拟知识文档的录入、审核、发布和检索。

### 3.2 第一阶段不包含

- LDAP 正式接入；
- 自动执行扩容、缩容、配置修改等生产变更；
- 以大模型输出替代确定性异常判定；
- Temporal、Qdrant、本地大模型或本地 Embedding 模型的生产部署；
- 配置文件分析接口的正式接入；
- 财务级成本结算与真实资源回收；
- 数据中台未来接口的最终协议。

## 4. 关键假设与待确认项

### 4.1 当前确定的假设

1. 当前“四个接口”是：昨日汇总、单实例历史趋势、服务器信息、系统画像。
2. `mock-20260806.txt` 中的“配置文件”示例不是第一阶段四接口之一，保留为后续扩展数据源。
3. 模拟数据之间允许不一致；测试数据将依据本文数据结构重新构造可关联场景。
4. 昨日汇总是数据源直接返回，不要求能够由历史趋势重新计算得到。
5. 外部接口字段与未来数据中台可能变化，平台通过适配器转换为稳定内部模型。
6. 确认异常可由 Agent 自动创建 JIRA；优化机会需要系统管理员或 SRE 确认后建单。
7. 高风险事项可按规则自动建单和通知，但任何生产变更仍需人工审批与执行。
8. 一个系统可以有多个管理员，一个 SRE 可以管理多个系统，Admin 可以查看全部系统。

## 5. 用户与权限

### 5.1 角色

| 角色 | 可见范围 | 主要能力 |
|---|---|---|
| 系统管理员 | 被授权的一个或多个系统 | 查看分析与证据、对话追问、确认优化建议、处理 JIRA、查看验证结果 |
| SRE | 被授权的多个系统 | 上述能力；发起专项分析、调整系统级规则建议、处理跨系统治理事项 |
| Admin | 全部系统 | 用户与授权、数据源、全局规则、知识发布、JIRA 映射和运行配置管理 |

### 5.2 授权规则

- 用户与系统为多对多关系，并记录在该系统中的职责：`OWNER`、`SRE`、`VIEWER`。
- 所有系统级查询必须在服务端应用授权范围，前端隐藏不构成安全控制。
- 对话检索、证据下载、JIRA 操作和 Agent 事件均继承当前用户的系统范围。
- Agent 后台巡检可以覆盖全部启用系统，但主动消息只投递给相应系统管理员、SRE 和 Admin。
- 第一阶段使用模拟身份切换；权限模型不得因模拟登录而省略。

## 6. 核心业务流程

### 6.1 每日自主巡检

```text
定时触发
→ 创建巡检批次
→ 拉取四接口并保存原始快照
→ 标准化、关联和数据质量检查
→ 计算特征并执行确定性规则
→ 按根因归并分析发现
→ 检索已发布知识和相似历史案例
→ 大模型生成解释与治理建议
→ 按行动策略自动建单或等待确认
→ 发布今日简报、工作事件和主动消息
```

每一步必须记录状态、输入版本、输出摘要、耗时和错误，失败步骤应支持幂等重试；单个系统失败不应阻塞其他系统完成巡检。

### 6.2 用户对话与干预

用户可以询问：

- “我负责的系统昨天有哪些容量风险？”
- “为什么 GreatDB 被判为异常，而不是正常增长？”
- “展示该实例近 30 天 CPU、内存和磁盘趋势。”
- “优先分析核心系统的磁盘增长风险。”
- “这个缩容建议先不要建单，观察 7 天。”

Agent 回答必须区分事实、推断和建议；事实应引用证据快照，规则结论应引用规则版本，知识性建议应引用知识版本。用户对分析方向的修改只影响授权范围内的后续计划，不得直接触发生产变更。

### 6.3 异常到 JIRA

```text
分析发现
├─ 确认异常：Agent 自动创建或关联 JIRA
├─ 优化机会：等待负责人确认后创建 JIRA
├─ 预期偏离：记录结论，不创建 JIRA
└─ 待复核：创建内部复核事项，不自动创建 JIRA
```

同一根因在去重窗口内只关联一个未完成治理事项。高风险异常应立即通知责任人；普通确认异常可在每日巡检完成后批量通知。

### 6.4 治理完成与效果验证

```text
JIRA 进入完成态
→ 治理事项进入观察期
→ 按治理类型读取观察周期和验收规则
→ 每日拉取新数据并与治理前基线比较
→ 验证成功：关闭治理事项并沉淀案例
→ 验证失败：重新打开 JIRA或创建关联跟进单
→ 证据不足：延长观察或转人工复核
```

JIRA 完成不等于治理成功。只有效果验证通过，治理事项才能进入 `VERIFIED`。

## 7. 页面与交互需求

### 7.1 Agent 首页

- 聊天是主交互区，支持流式回答、证据引用和推荐追问。
- 同时显示“今日巡检简报”和“正在跟进的任务”。
- 显示 Agent 当前工作、刚完成工作和下一步计划，而非仅显示静态在线状态。
- 自主工作通过服务端事件实时推送；用户无需点击即可看到取数、分析、建单、同步和验证进度。
- 主动消息可下钻到系统、发现、证据、建议和 JIRA。

### 7.2 系统总览与详情

- 系统总览只显示用户有权访问的系统，并按风险、浪费、倾斜和治理优先级排序。
- 系统详情支持日期选择，并从系统下钻至组件类型、逻辑资源和服务器实例。
- CPU、内存和磁盘统一展示平均值、峰值和最小值；历史缺失的指标明确显示“数据缺失”，不得显示为 0。
- 趋势图显示实际值、动态基线、阈值、预测区间和治理时间点。

### 7.3 数据证据

- 显示本次结论使用的源接口、采集时间、数据窗口、原始值、派生特征和规则版本。
- 显示画像关联路径及匹配置信度。
- 显示 AI 建议引用的知识条目与版本。
- 支持从发现、建议、JIRA 和验证记录反向追溯同一证据链。
- 原始快照对普通用户只读，敏感字段按权限脱敏。

### 7.4 治理任务

- 统一展示内部治理事项和外部 JIRA 状态。
- 支持按系统、严重度、负责人、阶段、逾期和验证结果筛选。
- 时间线包含发现、建议、确认、建单、状态同步、治理完成、观察和验证事件。
- 系统管理员处理 JIRA，Agent 负责创建、同步、提醒和复核。

### 7.5 知识管理

- 支持内置、上传、手工录入和仓库同步四类知识来源；模型生成内容只能进入草稿。
- 知识状态为 `DRAFT`、`REVIEWING`、`PUBLISHED`、`SUPERSEDED`、`EXPIRED`。
- 只有 `PUBLISHED` 且在有效期内的知识可参与正式建议。
- 支持适用系统、组件类型、角色、治理类型、标签和生效时间过滤。

## 8. 四个外部数据接口

### 8.1 通用接入要求

真实 URL 与认证方式尚未提供，第一阶段为每类数据定义独立适配器。每次调用必须记录：`source_type`、`request_key`、`requested_at`、`responded_at`、`http_status`、`schema_version`、`payload_hash`、`raw_payload`、`error_code` 和 `error_message`。

标准化处理遵循：

1. 原始响应不可覆盖，只追加快照。
2. 字符串数字转换失败时标记数据质量问题，不默认为 0。
3. 指标统一为百分比，范围原则上为 `0.00–100.00`；超界值保留原值并标记异常数据。
4. 时间统一存储为 UTC，界面按 `Asia/Shanghai` 展示。
5. 外部枚举保留原值，并映射为内部稳定枚举。

### 8.2 IF-01 昨日性能容量汇总

**用途**：返回指定系统昨日各组件类型、逻辑资源和服务器实例的 CPU、内存、磁盘汇总。<br>
**当前示例**：[mock1.txt](../mock1.txt)

请求参数：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `system` | string | 是 | 系统稳定标识；当前 mock 为空，仅作为结构占位 |
| `date` | date | 是 | 业务日期，第一阶段默认昨天 |

响应外层：

| 路径 | 类型 | 必填 | 映射 |
|---|---|---:|---|
| `code` | integer | 是 | 外部请求状态；示例 `200` |
| `msg` | string | 否 | 外部消息 |
| `data.analysis_params.system` | string | 否 | 请求回显 |
| `data.analysis_result` | object | 是 | `组件类型 → 逻辑资源 → 汇总对象` |

逻辑资源汇总：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `code` | integer | 是 | 外部基线码：`0` 正常、`1` 警告、`2` 异常；只作输入信号 |
| `desc` | string | 否 | 外部描述，不作为平台最终结论 |
| `data` | array | 是 | 服务器实例汇总列表 |

服务器实例字段：

| 外部字段 | 类型 | 必填 | 内部字段 |
|---|---|---:|---|
| `hostname` | string | 是 | `hostname` |
| `ip` | string | 否 | `ip_address` |
| `sn` | string | 否 | `serial_number` |
| `component` | string | 是 | `component_code` |
| `cpu` | string/number | 否 | `cpu_cores` |
| `memory` | string/number | 否 | `memory_gb` |
| `idc` | string | 否 | `idc_code` |
| `os` | string | 否 | `os_name` |
| `role` | string | 否 | `deployment_role` |
| `code` | integer | 是 | `source_baseline_code` |
| `exceptions` | array | 否 | `source_exceptions`，原样留存 |
| `CPU平均值/峰值/最小值` | number | 是 | `CPU.avg/max/min` |
| `内存平均值/峰值/最小值` | number | 是 | `MEMORY.avg/max/min` |
| `disk平均值/峰值/最小值` | number | 是 | `DISK.avg/max/min` |

校验规则：每项指标应满足 `min <= avg <= max`；不满足时保留原始数据，标准化记录标为 `INVALID`，不进入自动异常判定。

### 8.3 IF-02 单实例历史趋势

**用途**：按服务器实例和时间范围返回 CPU、内存、磁盘趋势。<br>
**当前示例**：[mock-20260806.txt](../mock-20260806.txt) 第 1 节。

请求参数：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `resource_key` | string | 是 | 稳定资源 ID、SN、hostname 或 IP |
| `start_date` | date | 是 | 起始日期 |
| `end_date` | date | 是 | 结束日期，含当日 |
| `metrics` | array | 否 | 默认 CPU、MEMORY、DISK |
| `aggregation` | string | 否 | 默认 `DAILY` |

响应字段：

| 路径 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `data[].code` | integer | 否 | 外部状态码 |
| `data[].title` | string | 是 | 当前通过标题映射指标，如“CPU月度指标” |
| `data[].timeline[]` | date/datetime | 是 | 时间序列 |
| `data[].data[]` | number | 是 | 与 `timeline` 等长的指标值 |
| `data[].remark` | string | 否 | 外部备注 |
| `meta.cpu` | number | 否 | CPU 核数 |
| `meta.memory` | string/number | 否 | 内存 GB |
| `meta.hostname` | string | 是 | 主机名 |
| `meta.ip` | string | 否 | IP |
| `meta.idc_code` | string | 否 | IDC 编码 |
| `meta.os` | string | 否 | 操作系统 |

当前 mock 只有 CPU、内存历史序列。磁盘序列缺失时必须生成 `MISSING_METRIC:DISK` 数据质量发现，不允许从昨日汇总反推历史序列。正式接口建议新增稳定字段 `metric`、`unit`、`statistic`，避免依赖中文 `title` 解析。

### 8.4 IF-03 服务器硬件信息

**用途**：为物理机提供物理盘、逻辑盘和 RAID 上下文，辅助磁盘容量风险分析。<br>
**当前示例**：[mock-20260806.txt](../mock-20260806.txt) 第 3 节。

请求参数：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `resource_key` | string | 是 | 优先 SN，兼容 hostname/IP |

成功响应：

| 路径 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `物理盘[].name` | string | 是 | 物理盘名称 |
| `物理盘[].serialnumber` | string | 否 | 盘序列号，可能脱敏 |
| `物理盘[].size` | number | 是 | 容量，当前示例单位推定为 GB |
| `物理盘[].media` | string | 否 | SSD/HDD 等介质 |
| `物理盘[].bus` | string | 否 | 总线类型 |
| `物理盘[].firmware` | string | 否 | 固件版本 |
| `逻辑盘[].name` | string | 是 | 逻辑盘名称 |
| `逻辑盘[].size` | string/number | 是 | 容量，标准化为 GB |
| `逻辑盘[].disk` | string | 否 | 物理盘成员原始描述 |

### 8.5 IF-04 系统画像

| `链路[].fnode` | string | 是 | 上游逻辑资源 |
| `链路[].snode` | string | 是 | 下游逻辑资源 |
| `链路[].module` | string | 否 | 链路所属组件类型原值 |
| `集群关系.{组件类型}[].clusterName` | string | 是 | 集群名称 |
| `集群关系.{组件类型}[].nodes[]` | array | 是 | 集群包含的逻辑资源名称 |

### 8.6 资源关联规则

关联顺序：

1. 统一资源 ID/CMDB ID（未来接口提供后启用）；
2. 完整 SN 精确匹配；
3. 规范化 hostname 精确匹配；
4. IP 精确匹配；
5. hostname + IDC + component 组合匹配；
6. 无法唯一匹配时进入 `NEEDS_REVIEW`，不得猜测归属。

每次关联保存 `match_method` 和 `match_confidence`。SN/hostname/IP 冲突时，不自动合并资源，创建 `RESOURCE_IDENTITY_CONFLICT` 数据质量发现。

## 9. 异常识别策略

### 9.1 分层判定

平台不得直接把外部 `code` 当作最终异常。判定顺序为：

```text
源基线码
→ 数据质量门禁
→ 固定阈值与持续性
→ 动态基线、趋势和预测
→ 系统画像与部署角色
→ 集群/链路归因和事件归并
→ 最终分析发现
```

最终状态：

| 状态 | 含义 | 默认动作 |
|---|---|---|
| `NORMAL` | 未发现需关注偏离 | 记录 |
| `EXPECTED_DEVIATION` | 偏离通用基线但符合架构预期 | 记录并解释 |
| `ANOMALY` | 证据充分的容量风险或异常 | 自动创建/关联 JIRA |
| `OPTIMIZATION_OPPORTUNITY` | 有资源优化价值但无即时风险 | 等待确认后建单 |
| `NEEDS_REVIEW` | 数据缺失、冲突或规则证据不足 | 内部复核，不自动建 JIRA |

### 9.2 冷启动默认规则

阈值采用百分比点（pp），均为可版本化配置；系统级、角色级、组件级规则可覆盖全局规则，优先级为：`系统 > 部署角色 > 组件类型 > 全局`。

| 规则 | 默认条件 | 最低证据 | 初始严重度 |
|---|---|---|---|
| CPU 高使用 | 昨日平均 `>=70%` 或峰值 `>=85%` | 历史近 3 点至少 2 点同向，或峰值连续 2 日越界 | P2 |
| 内存高使用 | 昨日平均 `>=75%` 或峰值 `>=90%` | 历史近 3 点至少 2 点同向 | P2 |
| 磁盘高水位 | 昨日平均 `>=75%` 或峰值 `>=85%` | 汇总有效；历史存在时需同向佐证 | P2 |
| 磁盘紧急风险 | 峰值 `>=90%`，或预测 7 天内达到 90% | 至少 7 个历史点；预测需 `R²>=0.5` | P1 |
| 持续低利用 CPU | 近 14 日平均 `<15%` 且峰值 `<30%` | 14 个有效日，业务/角色规则不豁免 | P3 优化机会 |
| 持续低利用内存 | 近 14 日平均 `<25%` 且峰值 `<40%` | 14 个有效日，业务/角色规则不豁免 | P3 优化机会 |
| 快速增长 | 7 日线性斜率：CPU/内存 `>=10pp`，磁盘 `>=5pp` | 至少 7 点且 `R²>=0.5` | P2 |
| 集群负载倾斜 | 同逻辑资源至少 3 实例，峰值 `max-min>=30pp` | 同一业务日、同一指标 | P2 |
| 数据缺失 | 必需指标、日期或身份字段缺失 | 采集快照可追溯 | P3 数据质量 |

规则补充：

- CPU 单点峰值越界但历史不持续时，默认为 `NEEDS_REVIEW`，不直接建单。
- 内存高位且趋势平稳仍可构成风险，不能仅依赖斜率。
- 磁盘“低使用率”不是默认优化机会，磁盘回收需结合盘容量、RAID、挂载和业务约束。
- 冷备、灾备、只读副本等低利用可由已发布角色规则判为 `EXPECTED_DEVIATION`。
- 系统画像过期、角色缺失或资源匹配置信度低于 0.8 时，禁止自动判定低利用优化机会。
- 外部源 `code=2` 但平台证据不足时仍为 `NEEDS_REVIEW`；平台必须解释差异。

### 9.3 动态基线与预测

- 动态基线默认使用同一实例、同一指标最近 30 个有效日的中位数与 MAD。
- 偏离度：`abs(current - median) / max(1.4826 * MAD, 5)`。
- 偏离度 `>=3` 记为强偏离证据，`2–3` 记为弱偏离证据。
- 趋势预测使用最近 7–30 个有效日的线性回归；少于 7 点或 `R²<0.5` 时不输出“预计几天达到阈值”。
- 预测值只作为风险加权证据，不取代阈值、角色和集群上下文判断。

### 9.4 置信度与严重度

置信度由确定性证据计算，大模型不得修改：

| 证据 | 权重 |
|---|---:|
| 固定阈值命中 | 25 |
| 持续性成立 | 20 |
| 动态基线强偏离 | 15 |
| 趋势/预测成立 | 15 |
| 画像与角色证据完整 | 15 |
| 集群或链路交叉验证 | 10 |

`confidence = 已满足权重之和 / 可用证据权重之和 * 100`。自动创建 JIRA 的默认门槛为：最终状态 `ANOMALY`、置信度 `>=80`、资源匹配置信度 `>=0.8`、不存在阻断性数据质量问题。

严重度综合资源风险与系统重要性：

| 严重度 | 示例 | 行动时限 |
|---|---|---|
| P1 | A 级系统磁盘已达 90% 或 7 天内触达 | 立即建单并通知，4 小时内响应 |
| P2 | 持续高使用、快速增长、显著集群倾斜 | 自动建单，1 个工作日内响应 |
| P3 | 低利用优化、一般数据质量问题 | 优化需确认；数据质量进入内部任务 |
| P4 | 信息提示或弱偏离 | 仅报告 |

### 9.5 事件归并和去重

发现指纹默认由 `system_id + finding_type + metric + scope_type + scope_id + root_cause_key` 生成。相同指纹在未解决治理事项或 7 日去重窗口内合并：更新最新证据、发生次数和严重度，不重复创建 JIRA。多个实例由同一逻辑资源倾斜导致时优先归并为逻辑资源级发现。

## 10. AI 分析与治理建议

### 10.1 职责边界

- 算法/规则负责数据校验、特征计算、异常状态、严重度和置信度。
- 大模型负责多源信息综合、原因解释、候选方案、风险提示和面向用户的回答。
- Agent 编排负责计划、调用工具、建单、状态跟进、通知和效果验证。
- 大模型不得直接执行生产变更、篡改证据或越过自动化门槛。

### 10.2 建议输入

每次建议至少包含：发现 ID、资源范围、系统重要性、指标窗口、汇总值、历史特征、集群对比、画像角色、命中规则、数据质量状态、相关已发布知识和相似已验证案例。

### 10.3 建议输出结构

| 字段 | 类型 | 说明 |
|---|---|---|
| `summary` | string | 一句话结论 |
| `diagnosis` | string | 原因分析，区分事实与推断 |
| `evidence_refs[]` | array | 必须引用证据项 ID |
| `knowledge_refs[]` | array | 引用知识版本 ID，可为空 |
| `actions[]` | array | 按顺序列出操作建议、负责人类型、风险和回退条件 |
| `expected_effect` | string | 预期指标变化 |
| `observation_type` | enum | 对应观察周期配置 |
| `risks[]` | array | 执行风险和限制 |
| `confidence_note` | string | 解释规则计算的置信度，不自行生成分数 |

如果没有 `evidence_refs`，建议不得发布或写入 JIRA。知识检索失败时可以基于通用能力给出保守建议，但必须标注“未引用内部治理知识”，且不得生成高风险操作步骤。

### 11.3 去重、同步与状态映射

- 创建前使用发现指纹查询平台未完成治理事项，不依赖 JIRA 文本搜索去重。
- 请求使用 `idempotency_key`，网络超时后先按已保存的请求标识核对再重试。
- 优先接收 JIRA webhook；同时每 10 分钟增量对账，避免 webhook 丢失。
- JIRA 状态名称不硬编码，通过配置映射到内部状态：

| JIRA 状态类别/配置 | 内部状态 |
|---|---|
| To Do | `TICKET_OPEN` |
| In Progress | `TICKET_IN_PROGRESS` |
| Done 且 resolution 非空 | `OBSERVING` |
| Cancelled/Won't Do | `CANCELLED` 或 `NEEDS_REVIEW` |
| Reopened | `TICKET_IN_PROGRESS` |

Agent 可以创建、评论、同步和提醒，不自动执行 JIRA 中描述的生产操作。验证失败时，优先 reopen 并评论新证据；无 reopen 权限时创建关联跟进单。

## 12. 治理类型与观察策略

| 治理类型 | 默认观察期 | 采样频率 | 默认成功条件 |
|---|---:|---|---|
| 磁盘清理/归档 | 7 天 | 每日 | 峰值低于 80%，日增速低于 1pp，无再次越界 |
| 扩容 | 7 天 | 每日 | 峰值回到规则安全区，且无新负载倾斜 |
| 缩容/降配 | 14 天 | 每日 | 覆盖至少一个业务高峰；CPU/内存峰值低于高阈值并保留安全余量 |
| 负载均衡/权重调整 | 7 天 | 每日 | 实例极差低于 20pp，且整体峰值不恶化 |
| 配置/查询优化 | 7 天 | 每日 | 目标指标相对治理前基线改善至少 20%，且无副作用证据 |
| 数据质量修复 | 3 次成功采集 | 每次巡检 | 连续 3 次完整、可关联、无同类错误 |

观察策略可按系统和治理类型覆盖。验证基线使用治理动作前 7–30 个有效日，具体窗口随策略保存，保证日后可复现。

## 13. 非功能需求

### 13.1 可用性与性能

- 首页常规查询 P95 小于 2 秒，不包含大模型生成时间。
- Agent 流式首事件目标小于 3 秒；长任务先返回工作事件，不阻塞请求。
- 每日巡检支持按系统隔离重试；重复触发不得产生重复发现和 JIRA。
- 第一阶段单机部署，API、Worker、Scheduler 独立进程，可分别重启。

### 13.2 安全与审计

- 密钥、Token、密码只通过环境变量或部署密钥文件提供。
- 所有外部写操作、知识发布、人工确认、规则变更和权限变更记录审计。
- 对话不得泄露用户未授权系统的数据。
- 原始响应可包含敏感 IP/SN，展示和导出按角色脱敏。
- 防止提示注入：知识文档和接口文本均视为数据，不能改变 Agent 系统策略或工具权限。

### 13.3 可解释与可复现

- 每个分析发现必须关联分析批次、证据、规则版本和输入快照。
- 每个 AI 建议必须保存模型、提示模板版本、检索条目和结构化输出。
- 相同证据和规则版本应得到相同异常状态、严重度和置信度；允许语言表述不同。

### 13.4 兼容与部署

- 前端：Vue 3 + TypeScript，构建后静态部署。
- 后端：Python 3.12 + FastAPI，原生虚拟环境和 systemd，不为本项目新增 Docker 依赖。
- 数据库：MySQL 5.7；缓存/队列：Redis 7.x。
- 开发大模型：DeepSeek 公网 OpenAI 兼容 API；生产：公司内部 OpenAI 兼容网关。
- 第一阶段部署到开发服务器 1；开发服务器 2 保留静态演示页。

## 15. 第一阶段成功指标

- 四接口采集成功率不低于 99%（排除数据源计划维护）。
- 可关联服务器实例比例不低于 95%，所有低置信度关联可追踪。
- 自动建单重复率低于 1%。
- 所有已发布建议的数据证据引用完整率 100%。
- 试运营确认异常准确率目标不低于 85%，并按规则版本统计。
- JIRA 完成后的自动验证覆盖率不低于 95%。
- 用户在首页可以无需手工触发地看到每日巡检、异常建单和治理跟进进度。
